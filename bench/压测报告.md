# 抢奖接口压测报告

> 测试时间：2026-11-04
> 被测对象：`POST /api/lottery/join/{roundId}`（秒杀入口）
> 测试脚本：`bench/bench_join.py`

---

## 一、测试环境

| 项 | 配置 |
|---|---|
| 机器 | 单机 Windows 11，Docker Desktop |
| 后端 | Spring Boot 3.2.5 / JDK 17，容器内 1 实例 |
| Redis / MySQL / RabbitMQ | 同机 Docker 容器 |
| 压测客户端 | Python 3.13，`http.client` 连接复用，与后端**抢同一台机器的 CPU** |

**这个环境有两个硬限制，看数据时必须带着：**

1. 压测客户端和后端抢同一台机器的 CPU，客户端越猛，服务端拿到的 CPU 越少。
2. Python 有 GIL，100 线程以上客户端自身先饱和。

所以下面的数字是「本机能观测到的水平」，不是服务端上限。

---

## 二、场景与结果

### 场景 1：顺利路径（500 用户抢 500 个名额，50 线程）

服务刚启动，未预热：

| 轮次 | 吞吐 | avg RT | p50 | p90 | p99 |
|---|---|---|---|---|---|
| 第 1 轮（冷启动） | 795 req/s | 50.9 ms | 44.4 ms | 83.8 ms | 172.1 ms |
| 第 2 轮 | 970 req/s | 35.7 ms | 35.4 ms | 57.9 ms | 72.2 ms |
| 第 3 轮 | 1148 req/s | 18.8 ms | 17.1 ms | 32.2 ms | 49.0 ms |
| 充分预热后 | 1581 req/s | 18.4 ms | 17.9 ms | 29.6 ms | 36.6 ms |

**结论：冷启动的 p99 是稳定态的 3.5 倍（172ms vs 49ms）。**
JIT 没编译完之前，同一个接口的耗时完全是两个量级。这条对生产有意义——服务刚发布时不该立刻承接大流量。

### 场景 2：规模翻倍（1000 用户抢 1000 个名额，100 线程）

| 吞吐 | avg RT | p50 | p90 | p99 |
|---|---|---|---|---|
| 1775 req/s | 35.9 ms | 34.3 ms | 65.0 ms | 88.7 ms |

吞吐比场景 1 只高 12%，RT 却翻倍——**客户端线程数翻倍带来的调度开销，比服务端处理能力增长更快**。这里已经不是服务端在决定了。

### 场景 3：竞争路径（500 用户抢 100 个名额，50 线程）

| 吞吐 | avg RT | p50 | p90 | p99 |
|---|---|---|---|---|
| 2835 req/s | 10.9 ms | 10.1 ms | 17.8 ms | 31.7 ms |

结果分布：成功 100、名额已满 81、轮次已结束 319、重复 0、跨轮次 0、**异常 0**。

**这条数据最有价值：**
- 失败路径比成功路径快 1.7 倍（10.9ms vs 18.8ms），因为成功要投 MQ、失败只读一次 Redis。
- 319 个「轮次已结束」说明名额抢完后轮次被自动收尾，后续请求被前置拦截，没有继续打到 Lua 扣减。
- 100 个名额、100 个中奖记录、库存扣到 0，**零超卖**。

### 场景 4：500 并发瞬间（500 线程一次性打）

| 吞吐 | avg RT | p99 |
|---|---|---|
| 488 ~ 515 req/s | 201 ~ 224 ms | 475 ~ 618 ms |

这批数据**不能用来评价服务端**。500 个 Python 线程同时创建、同时发请求，线程调度和 GIL 争抢本身就是 200ms 级别的开销。

## 三、调优动作

| # | 动作 | 依据 | 可量化收益 |
|---|---|---|---|
| 1 | Lettuce 连接池 `max-active` 8 → 64 | 连接数小于并发在途请求数时，请求排队等连接 | 本机测不出（客户端先饱和），配置本身合理 |
| 2 | Tomcat `threads.max` 200 → 500、`accept-count` 1000 | 默认 200 线程在 500 并发时会排队 | 同上 |
| 3 | 在线人数广播：每次连接/断开 → 每 2 秒检查变化 | 2000 人进场 = 2000 次广播 × 平均 1000 连接 ≈ 200 万次推送 | 未单独压测，属于结构性修复 |

**没有做假对比。** 第 1、2 项在本机环境下无法量化收益，因为压测客户端先成为瓶颈；把这两项写成「性能提升 2 倍」是不诚实的。

## 四、发现的问题

### P1 冷启动 RT 放大 3 倍
- 现象：同接口冷启动 p99 172ms，预热后 49ms。
- 影响：服务刚发布、容器刚重建时接流量会明显抖动。
- 建议：加一个启动预热任务（预热 Lua 脚本、连接池、JIT 热点方法），或发布时先放小流量。

### P2 「名额已满」与「轮次已结束」语义重叠
- 现象：名额抢完后轮次立刻被置为已结束，之后到达的请求拿到的是 `-3 本轮已结束`，而不是 `0 名额已满`。
- 影响：用户看到「本轮已结束」比「手慢了」体验差；统计上也容易把正常业务分支误判为异常。
- 建议：轮次结束后保留一个短暂的「售罄」状态，或把文案统一成「本轮奖品已抢完」。

### P3 压测方法本身
- 首版脚本每个用户一个线程，500 用户就是 500 线程，测出来的是客户端能力。
- 已改为「线程复用连接、每个线程顺序处理一批 token」，数据才反映服务端。

## 五、局限与下一步

**没做到的：**
- 没在独立压测机上跑，服务端真实上限未知。
- 没测 2000 长连接的 WebSocket 广播延迟（需要独立的 WS 压测工具）。
- 没做长时间稳定性压测（分钟级持续打），只测了秒级峰值。

**下一步：**
1. 用 wrk 或 JMeter 在另一台机器上重跑，拿到服务端真实 QPS 上限。
2. 补 WebSocket 场景：2000 连接 + 每秒 200 条弹幕，测广播延迟 p99。
3. 加启动预热，把这部分收益量化出来。
